## BUG-001 · 视频目录死锁：零目录时教师无法建第一个目录

**严重度**：🔴 高（**功能在空库上完全不可用**，且提示语撒谎）

**发现者**：用户实测（截图）· 复核：Lead 读码确认

### 症状
教师打开视频页（`#/video`），看到：

```
视频目录 0 个                      [刷新]
┃ 还没有视频目录（教师可新建）        ← ★ 提示说"教师可新建"
[全部视频]
```

★ **但页面上没有输入框、没有「新建目录」按钮、没有「上传视频到该目录」按钮** ——
**提示语声称的"可新建"没有任何入口。**

### 根因（已定位到行）
```ts
// apps/web/src/views/Chat.vue（视频页同款问题）
// apps/web/src/views/Video.vue:82
const canManage = computed(() => collections.value.some((x: CollectionInfo) => x.can_manage === true))
// apps/web/src/views/Video.vue:692
<div v-if="canManage" class="coll-ops" data-testid="collection-teacher-ops">   ← 教师操作区
// apps/web/src/views/Video.vue:90
if (!collections.value.length) collectionsNote.value = '还没有视频目录（教师可新建）'
```

★★★ **死锁**：`canManage` 的判据是"**有没有任何一个目录归我管**"——
**零目录 → `canManage=false` → 操作区不渲染 → 无法建出第一个目录**。

★ 该文件 L78-80 的注释**已经点到了这个坑**（"实测踩到 `collection-teacher-ops` 不渲染"），
但当时的修法只解决了"**当前选中项不是目录**"的情况，**没解决"零目录"**。

### 复现
```
① 清空 collections 表（或用一个全新库）
② 用 teacher 登录 → 打开 #/video
③ 观察：看不到任何建目录入口（且提示语说"教师可新建"）
```

### 影响
- **全新部署的教师完全无法创建第一个课程系列目录**（必须先用 API 手工建一个才能解锁 UI）
- 提示语与事实不符（"教师可新建"）—— 属于"看起来能用"一类

### 临时绕过（Lead 实测有效）
用 API 先建一个目录，再点页面「刷新」：
```bash
curl -b cookies -X POST http://127.0.0.1:8787/api/v1/collections \
  -H 'Content-Type: application/json' -d '{"name":"临时"}'
```

### 修法方向（**未实施**）
| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | **服务端暴露"我能不能建目录"能力位**（如 `/capabilities` 或 `/me` 加 `collections.can_create`），前端用它 | ★ 与代码既有原则一致："权限用**服务端计算**的 can_manage，前端不自己推断"（坑 21 同族）。"能不能建"是**权限问题**，与"当前有没有目录"无关 |
| B | 零目录时也显示操作区，让后端在 POST 时判权限（403 如实报） | 能解死锁，但**学生会看到建目录入口**（点了 403） |
| C | 前端用自己的角色判断 | ✗ **前端推断权限** —— 正是注释里反对的做法 |

### 必需的回归断言
```
★ 造一个"零目录"夹具 → 断言 collection-teacher-ops **可见** + 「新建目录」可点
   （现有断言只覆盖"有目录时可见" —— 这正是漏掉死锁的原因）
★ 反例：**学生**（零目录）→ 操作区**不可见**（不能为了修死锁把学生也放开）
★ 提示语不许撒谎：要么给入口，要么改文案
```

## BUG-002 · 切换会话后消息加载不出来，且无法继续对话

**严重度**：🔴 高（**对话功能的主路径不可用**）

**发现者**：用户实测 · 复核：Lead（WS 实测 + 读码）

### 症状（用户原话）
> "新建并对话之后点到别的对话，再回来**加载不出刚刚问的东西**，
> **要再创建一个对话才能对话**"

两个症状：
1. 切回旧会话 → **之前问过/答过的消息不显示**
2. 切回后**连输入都无法继续**（必须新建一个会话才能对话）

### 已实测确认的部分（★ 后端机制是好的）
Lead 用真 WebSocket 连到已有会话（**零 LLM**，只连接不发消息），帧序列如下：

| 会话 | 帧序列 | 说明 |
|---|---|---|
| `cnv_c1583ab4a5e6` | `['ready', 'history']` | ★★ **有历史 → 服务端确实发了 `history`，`messages=2`** |
| `cnv_ee337b2ca840` | `['ready']` | 无历史消息 → 不发（正常） |
| `cnv_f7321e3931c7` | `['ready']` | 无历史消息 → 不发（正常） |
| 新建会话 | `['ready']` | 新会话本来无历史（正常） |

⟹ ★★ **服务端在"会话有历史"时**确实发 `history` 帧（`apps/server/src/agent/session.ts:1099 hasHistory`）
⟹ ★ **所以缺陷在**前端**（收到却没正确铺上，或重连把状态弄坏了）

### 已定位的前端根因（高置信）
```ts
// apps/web/src/views/Chat.vue:993
function startSocket() {
  socket = new ChatSocket(chatSessionId.value, undefined, chatMode.value, props.assistant)
  //  ★★ 直接覆盖 socket 引用 —— **没有先关闭旧连接**
  socket.onState(...)
  socket.on('*', onEvent)
}

// apps/web/src/views/Chat.vue:889
function switchSession(id: string) {
  if (id === chatSessionId.value) return
  chatSessionId.value = id
  persistSessionId(id, !props.embedded)
  msgs.value = []
  ...
  startSocket()          // ← ★ 调用的就是上面那个"不关旧连接"的函数
}
```

★ `ChatSocket.close()` **是存在的**（`apps/web/src/api/chat.ts:163`），
Chat.vue 也**有两处**在调它（L799 重连路径 · L1054 组件卸载），
★★ **但 `startSocket()` 这条路径漏了** ⟹ **每次切会话泄漏一个 WebSocket，旧连接永远活着。**

### 推测的因果链（**待实测确认**）
```
① 旧 socket 仍活着 → 其 onmessage 仍触发 onEvent（旧实例的事件仍绑着）
   → ★ **旧会话的帧混进新视图** → 消息列表错乱 / 铺不上
② 泄漏的连接可能占住服务端的 agent 会话资源
   → ★ **新连接初始化失败** → "要再创建一个对话才能对话"
   ⚠️ 第 ② 条**尚未证实**：`session.ts:582-588` 对"同用户已存在"是 `return`（复用）而非拒绝，
      所以机制可能更微妙（需要 WS 层实测：连续切换 N 次后观察连接数与可对话性）
```

### 复现（建议的验证脚本）
```
① 打开 #/chat → 新建会话 A → 发一句 → 等回答
② 点会话 B（随便一个）→ 再点回 A
③ 观察：A 的消息是否显示？输入框能否继续对话？
④ ★ 同时在浏览器 DevTools → Network → WS 里数**同时打开的 WS 连接数**
   （若每切一次 +1 → 直接证明泄漏）
⑤ 服务端侧：看 `data/logs/app-YYYY-MM-DD.log` 里该会话的连接/断开记录
```

### 修法方向（**未实施**）
```
★ 最小修法：`startSocket()` 开头先关旧连接
   function startSocket() {
     try { socket?.close() } catch { /* ignore */ }
     socket = new ChatSocket(...)
     ...
   }
★ 更稳的做法：`ChatSocket` 内部或 Chat.vue 维护"当前连接"单例，切换时显式 close + await 关闭完成
   （避免"新连接已开、旧连接还在收帧"的重叠窗口）
★ 并加断言：**切换 N 次会话后，打开的 WS 连接数 === 1**
   （DOM/WS 层断言；★ 这条断言现在**不存在** —— 这正是泄漏没被发现的原因）
★ 顺带核对 `history` 帧的铺回逻辑（`Chat.vue:611-638`）：
   它在 `msgs` 非空时**只追加缺失的**（去重）——若泄漏的旧连接先塞进了别的会话的消息，
   这段去重就会把**真正的历史判成"已存在"而不铺** ⟹ 两条缺陷会**互相放大**
```
